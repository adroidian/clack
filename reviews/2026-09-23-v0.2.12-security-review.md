# Clack `v0.2.12` GitHub branch security review

Reviewed 2026-09-23. Target: [`adroidian/clack` `v0.2.12`](https://github.com/adroidian/clack/tree/v0.2.12), six commits ahead of `main`. The reviewed local copies of `relay.py`, `relay-cli.py`, `ed25519.py`, `CLIENT_CONTRACT.md`, and three test scripts were checked against their GitHub blob hashes. This is a source review of the candidate branch, not a claim about the running service. The [deployment runbook](https://github.com/adroidian/clack/blob/v0.2.12/DEPLOY_ROLLBACK_v0.2.12.md) says production is still v0.2.11 and deployment awaits approval and signing-key readiness.

## Findings

### P1 — Unpinned clients send bearer tokens after unauthenticated identity downgrade

[`fetch_relay_identity()`](https://github.com/adroidian/clack/blob/v0.2.12/relay-cli.py#L646) converts *any* HTTP 503 from `/v1/identity` into `(None, None)`. In [`_ensure_origin_verified()`](https://github.com/adroidian/clack/blob/v0.2.12/relay-cli.py#L510), a config without `relay_identity_fingerprint` treats that result as an allowed first-contact condition, marks the origin verified, and returns. [`req()`](https://github.com/adroidian/clack/blob/v0.2.12/relay-cli.py#L559) then attaches its bearer token. This includes existing token-bearing configs that predate pinning; it is not confined to a new identity enrollment.

An isolated loopback server returned 503 to the challenge and then recorded `Authorization: Bearer sentinel-token` on the subsequent `/v1/peers` call. Someone who controls the configured relay endpoint can deliberately return 503 to collect credentials from an unpinned client. The new F4 test covers only a config *with* a pin, and explicitly treats 503 without a pin as acceptable.

Fail closed for token-bearing `req()` calls when the identity challenge is unavailable, regardless of whether a pin exists. If unauthenticated identity-less relay onboarding must remain possible, make it a separate, explicit, interactive enrollment path that does not transmit an existing bearer token.

### P2 — First-contact key is accepted without the contract's out-of-band confirmation

For a valid identity response and no existing pin, [`_ensure_origin_verified()`](https://github.com/adroidian/clack/blob/v0.2.12/relay-cli.py#L551) immediately stores the presented fingerprint and proceeds to the API request. There is no comparison with a fingerprint from an independently trusted source or a confirmation gate for ordinary `req()` calls. The [client contract](https://github.com/adroidian/clack/blob/v0.2.12/CLIENT_CONTRACT.md#L257) says to “confirm once out-of-band” before pinning. Merely printing the fingerprint on stderr after receiving it from the same endpoint is not that confirmation.

This is the inherent first-contact limit of automated TOFU, but it matters for the claimed threat model: a stolen/reassigned endpoint with a valid certificate can present its own key, become the stored pin, and receive the first bearer token. Either require a provisioned/confirmed fingerprint before secret-bearing requests, or document the weaker first-contact guarantee plainly and do not describe the challenge alone as endpoint authentication.

### P2, deployment-dependent — Source-IP limits may collapse all tunnel traffic into one bucket

[`/v1/identity`](https://github.com/adroidian/clack/blob/v0.2.12/relay.py#L1364) allows 30 requests/minute keyed to `self.client_address[0]`. The failed-auth limiter and enrollment paths use the same socket IP. The runbook places the listener at `127.0.0.1:18802` behind Cloudflare. If cloudflared connects to the listener from loopback, every remote user shares the `127.0.0.1` bucket. Because the CLI fetches `/v1/identity` before authenticated requests, 30 unauthenticated challenges in a minute could make subsequent client calls fail at the identity step. This is a conditional finding: I did not inspect the live tunnel configuration or verify the source address seen in production.

Confirm the actual source address at the handler. If it is shared, apply per-client controls at the trusted edge or derive client identity only from headers set and sanitized by that edge. Do not trust arbitrary forwarded-IP headers on a listener reachable by untrusted clients.

## Earlier findings and verification

The branch contains targeted fixes for all six earlier relay findings: retired peer mail/webhook cleanup, nonce-capacity fail-closed behavior, post-read freshness check, separate failed-auth rate accounting, rejection of low-order Ed25519 keys, and legacy invite gate enforcement. The source paths and dedicated tests support those fixes; this review did not establish production deployment.

- `test-peer-lifecycle.py`: 13 passed, 0 failed.
- `test-signing.py`: 72 passed, 0 failed.
- `test-client-security.py`: 18 passed, 1 failed. Its failed assertion requires POSIX `0600` mode bits on Windows. The tested file's Windows ACL lists only SYSTEM, Administrators, and OWNER RIGHTS with full control, so this result does not demonstrate a token disclosure. Use a platform-aware ACL check.
- Isolated 503 credential proof: passed and recorded the bearer on the API request.

No production traffic, production data, deployment, or repository changes were used for the proof.
